# v0.2.3 transcript-bottom fade audit

Observed in the official Codex Windows package `OpenAI.Codex_26.1013.3656.0_x64__2p2nqsd0c76g0` with GPTDaddy 0.2.2 active. The visible 32 px band was a normal `div` in the main document, not a pseudo-element or shadow DOM. It was the direct child of the transcript's sticky bottom spacer inside `.thread-scroll-container`. Its classes included `_background_…`, `_fade_…`, `from-surface`, `pointer-events-none`, and `absolute`.

Before the fix, computed `background-image` was `linear-gradient(to top in oklab, rgb(234, 247, 255) 0%, rgba(0, 0, 0, 0) 100%)`; computed `background-color` was transparent. The visible rectangle was 731 × 32 CSS pixels in the 1096 × 781 renderer viewport. The pseudo-elements had no content or background. The existing `#root main .bg-gradient-to-t.from-surface` rule did not match because this fade was not in `<main>` and did not have `bg-gradient-to-t`.

The new rule matches only this transcript-bottom fade structure and sets `background-image: none`. It does not hide or remove the element, its sticky parent, the scroll container, the composer, or floating controls. With the installed 0.2.3 controller, computed `background-image` was `none` and pointer events remained `none`. On controller removal the original gradient returned; reapplying settings restored `none`.

Validation: 31 automated tests passed. Real Codex screenshots before and after the installed upgrade showed the band disappear. A long conversation remained scrollable (about 5,212 CSS px of range) with the composer staying in place; ChatGPT/Work mode switching and reopening the affected conversation retained the rule. Renderer viewport tests at 850 × 650 and 1096 × 781 kept the fade disabled and composer present. Setup.exe upgraded the installed version to 0.2.3; the portable archive extracted, passed syntax checking, and its bundled `doctor` command recognized the verified Codex package. Local screenshots were kept out of the GitHub source and packages because conversation content can be private.

Limitation: CDP's `Browser.getWindowForTarget` returned `Browser window not found`, and resizing the process main HWND did not change the renderer viewport. Therefore physical Win32 window-resize behavior is not claimed as separately verified; the responsive renderer viewport was tested. Codex's pre-CDP startup splash remains outside this injection's reach.
