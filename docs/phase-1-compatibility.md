# 阶段 1：兼容性与架构调查

调查日期：2026-10-11 至 2026-10-12（Asia/Taipei）

## 本机目标

- 官方包：`OpenAI.Codex_26.1007.2314.0_x64__2p2nqsd0c76g0`
- 主程序名仍为 `ChatGPT.exe`，窗口标题仍显示 `ChatGPT`
- 必须通过 AppX 包身份、安装路径和主进程命令行联合识别，不能仅按进程名判断
- 当前运行实例带有 `--remote-debugging-address=127.0.0.1 --remote-debugging-port=9222`
- 该实例来自旧皮肤启动方式，不能证明普通开始菜单启动支持 CDP

## 官方扩展边界

Codex 插件公开结构包含 skills、应用连接和 MCP 服务。当前没有公开的
renderer DOM 注入、BrowserWindow 生命周期或壁纸宿主接口。AppX manifest
包含启动任务、`codex://` 协议和若干系统扩展，但没有可为普通启动追加
Electron 命令行参数的扩展点。

对本机官方包的只读检查发现，`early-bootstrap.js` 中
`CODEX_ELECTRON_CHROMIUM_SWITCHES` 的解析函数在 `buildFlavor !== Dev` 时
直接返回空数组。因此不能通过该环境变量给正式版普通启动安全地附加 CDP 参数。
这属于该版本本机文件的证据，不代表所有未来版本都相同。

2026-10-12 再检查：保存状态仍为 `enabled=true`，但 HKCU Run 中没有
`GPTDaddy` 项，控制服务 `127.0.0.1:34873` 和 CDP `127.0.0.1:9222` 均无监听。
这说明上次手动启动的守护进程没有跨会话存活，不能把配置存在磁盘误判为
重启后已播放。当前受限环境无法读取该次真实客户端进程和进行 Windows
重启测试，因此没有验证“普通图标启动自动出现壁纸”。

## 原 Wallpaper Engine Codex 审计

可保留：

- Steam 库和项目发现
- 严格的 `app://-/index.html` CDP 目标白名单
- 设置持久化、媒体转码思想和可逆清理

必须重构：

- 旧实现通过额外快捷方式传入 CDP 参数
- 启动器可对所有匹配的无 `--type=` ChatGPT.exe 主进程执行 `Stop-Process -Force`
- `document.hidden || !document.hasFocus()` 会把普通失焦当作暂停
- 大视频通过 base64 分块聚合为 Blob，会同时占用 Node、字符串、Uint8Array 和 Blob 内存
- 3 秒轮询恢复只能判断 DOM 是否存在，不能判断视频是否实际呈现新帧

## WorkDaddy 许可和迁移边界

WorkDaddy 为 AGPL-3.0-or-later。GPTDaddy 采用相同许可证，避免后续移植形成
许可证冲突。账号 Token、Cookie 和私有会话数据库相关做法不进入当前 MVP。

## 功能矩阵

- 可直接移植：项目扫描、配置存储、CDP 消息封装、严格目标过滤。
- 需要重构：持久背景宿主、媒体传输、冻结检测、焦点/最小化策略、守护进程。
- 需要官方接口：普通 AppX 启动时自动开放 CDP，或官方 renderer 插件挂载点。
- 当前不可安全实现：在一个已经普通启动且没有 CDP 的 Codex 进程上事后开启 CDP。

## 当前替代架构

1. CDP 已安全开放时：使用本项目的持久化 DOM 宿主和 Range 媒体服务。
2. CDP 未开放时：后台服务继续提供壁纸库和状态管理，但明确报告不可注入；不强退 Codex。
3. 后续验证：评估用户明确同意的一次性登录启动编排，以及独立透明合成窗口。
   前者不能与官方 StartupTask 竞态，后者必须通过输入穿透、DPI、多屏和可访问性测试后才能采用。

已实现用户级登录启动脚本（默认仅验证、不修改注册表），用于确保 GPTDaddy
守护进程在下次登录后自动运行并读取上次设置；它不能替代缺失的 renderer
接入通道。守护进程支持 CDP 断开后的重新发现，串行化同一窗口的注入操作，
并避免登录监督器与已运行实例持续抢占端口。控制面板已区分“配置已保存”
“壁纸已加载”“收到近期视频帧”。
2026-10-12：10 项自动测试通过；登录启动脚本 `-ValidateOnly` 通过。
未运行 `-Install`，未执行真实 Windows 重启和正常图标启动验收。

2026-10-12：用户已明确同意安装当前用户登录启动项。随后从 Codex 沙箱内
执行 `-Install`，Windows 返回 `Requested registry access is not allowed`；注册项
未写入。项目提供 `scripts/install-user-startup.cmd`，用于用户在普通桌面会话中
执行同一项 HKCU 变更。此项只解决守护进程跨登录运行，不解决正式版普通启动
缺少 CDP 注入入口的问题，因此不能据此声称已达到“正常图标启动即有壁纸”。

用户随后在普通桌面会话运行安装器。实测 `127.0.0.1:34873/health` 返回成功，
守护进程读取到已启用的壁纸 `2789854092`。守护进程所在桌面会话检测到官方包
`OpenAI.Codex` 版本 `26.1007.2314.0` 正在运行（PID 33032），但进程命令行没有
CDP，也没有任何可连接的主页面目标。最终状态为 `desired=true`、`active=false`、
`playbackHealthy=false`。这次结果证实“后台自动运行”已经生效，但当前正式版
普通启动仍无法把持久壁纸宿主装入 Codex renderer。

后续检查发现本机 9222 端口属于 WorkBuddy 页面，而非 Codex。GPTDaddy
现已改为从验证过安装路径的 Codex 主进程命令行读取 CDP 端口；没有已验证
端口时不连接任何 CDP 服务。Codex 关闭、重启或调试端口变化时，生命周期
管理器会移除旧连接并尝试连接新的已验证端口。这避免把其它 Electron
应用的调试端口误当作 Codex 的接入点。

新增一次性实机验收脚本 `scripts/validate-live-codex.cmd`。它只在用户已正常
关闭 Codex 后才启动官方程序的 CDP 测试会话，并记录真实帧回调、媒体时间、
冻结恢复次数。当前沙箱内的 Codex 正在运行且没有 CDP，尚未执行该实机验收；
脚本存在不能代替通过验收。视频健康状态现在要求至少收到一帧真实呈现回调，
冻结检测分别检查帧回调和媒体时间是否继续推进。
